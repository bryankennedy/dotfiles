### DOT-28 — remote/install.sh owns `~/.gitconfig.dotfiles`, not `~/.gitconfig`

**Decision.** The installer writes the shared git config, `[user]` stripped, to `~/.gitconfig.dotfiles` and overwrites that file whenever its text differs. Its only claim on `~/.gitconfig` is one `[include]` of that file at the top. A `~/.gitconfig` that already has the include is never rewritten, whatever else it holds.

**What went wrong.** The installer generated `~/.gitconfig` whole, and decided whether to regenerate it by comparing the existing file, `[user]` block stripped, with its own text. That comparison knew about exactly one foreign section. Configuration management then began writing a second one, a `[credential "<url>"]` helper, through `git config --global`. From then on the comparison failed on every run, the file was regenerated from the shared text, and the identity and the helper went with it. The original sat in `~/.dotfiles-backup/`, and nothing reported a change.

**Why two files, not a better comparison.** The other fix was to strip every section the managed text does not define before comparing. It would have stopped the needless rewrites, but the first real change to `git/.gitconfig` would still regenerate the file, so the rewrite would also have to carry the foreign sections across, every time, correctly. That keeps two writers on one file and makes the installer's parser the thing standing between a play and a lost credential helper. With two files each has one writer: `git config --global` writes `~/.gitconfig`, the installer writes `~/.gitconfig.dotfiles`, and a change to the shared config touches only the second.

**Why the include goes first.** Git reads an include where it appears, and later values win. Everything `git config --global` has written or will write lands after the include, so local settings override the shared defaults. `~/.gitconfig.local` is still included from the end of the managed file, which keeps the precedence it had before: above the shared defaults, below `~/.gitconfig` itself.

**The one migration.** A `~/.gitconfig` without the include is either missing or a whole file from the old installer. The installer rewrites it once: the include, then the existing file minus the lines the managed file now supplies. It drops lines, not sections. A key somebody added to `[core]` by hand is theirs and stays; a section left with nothing in it goes. The cost is that a line from an older version of the shared config, no longer in the managed text, is kept as if it were local and shadows the managed file until someone removes it. That is visible in a short file and loses nothing; dropping whole sections would have been tidier and could delete a setting nobody has a copy of. The original is backed up like any other overwritten file.

**What holds it in place.** `tests/remote/install-gitconfig.test.js` runs the real installer against a throwaway home: a converged `~/.gitconfig` with `[user]` and a foreign section must come back byte-identical with no backup directory, a stale managed file must be regenerated without touching `~/.gitconfig`, and a whole-file `~/.gitconfig` must migrate once, keep what is not ours, and then hold still.

**Supersedes.** The comparison described under "The remote installer is idempotent, so `changed` means something again" in `docs/security-baseline.md` (rewrite only when the `[user]`-stripped content differs) is replaced by this. Its conclusion stands: a play over a converged host changes nothing and mints no backup directory.
