### DOT-38 — The runner-cache acceptance stays on the runner; CI now holds its in-repo conditions

**Decision.** The baseline entry "The review job restores the runner cache" keeps runner cache isolation as its basis. It does not move to the digest checks in `.forgejo/ci/install-tools.sh`. `tests/invariants/forgejo-ci.test.js` gains two checks: every `actions/cache` step in `.forgejo/workflows/` uses an exact key built from `hashFiles('.forgejo/ci/install-tools.sh')` and has no `restore-keys`, and `install_claude()` checks `CLAUDE_BIN_SHA256` on both paths before it installs `claude` to `/usr/local/bin`. The entry now names the first check as a condition, says the digest checks are not its basis, and uses the house heading and "This expires if" wording.

**What prompted it.** The nightly review of 2026-10-05 asked for three things. First, rest the acceptance on the digest checks and on nothing executing from a cached path, with the runner as a second layer. Second, add matching re-verify conditions. Third, repair the cache comment in `claude-review.yml`, which it read as cut off mid-sentence and still calling the cache shared.

**Why the basis did not move.** The review read the workflow as it stood before PR #90 (INFRA-210). That PR, merged the same day, fixed the broken comment and changed what it claims. The comment now says the runner keeps a forged entry out and that the digest check only catches a corrupt one. A cache restore unpacks a tar archive, and the archive can write to any path in the container before `install-tools.sh` runs. A digest check on one file covers only that file, and a rule about one directory covers only that directory. Accepting the cache on that basis would claim a control that does not exist. The owner accepted the cache on the runner's footing (RNQ-32, MSPT-102). This repo cannot measure that isolation, which is the concern DOT-21 raised, so the entry points to INFRA-203 for the measurement. That is unchanged.

**What changed instead.** The entry's conditions that this repo can check are now checked by CI on every PR. The `pull_request` trigger condition was already covered by "runs only on pull_request_target" and "never exposes a secret to a pull_request run". The exact-key condition is new. The `CLAUDE_BIN_SHA256` check is kept because a corrupt entry would otherwise reach `PATH`. It is pinned as a corruption check, not as a condition of the acceptance.

**Reassess** if Forgejo's cache restore comes to verify the archive (for example, by a content digest the workflow supplies), or if the cached paths stop being restored as a tar archive. Either change would make an in-repo check meaningful as a basis.
