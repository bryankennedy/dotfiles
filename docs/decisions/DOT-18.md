### DOT-18 — Pass 2f names a record to enumerate; what it means is assessed in private

**Decision.** Pass 2f of `_agent/skills/security-audit.md` still tells the auditor to note an `auto_mode` attachment that carries `bashFirst: true`. It no longer says what that record changes. That assessment, and how it reads against each machine's permission mode, lives in the private infrastructure repo's `docs/security-findings.md`. The auto-mode entry in `docs/security-baseline.md` was reopened, re-examined against that assessment, and re-accepted with a narrower statement of what the empty `permissions.allow` list contributes.

**What prompted it.** The nightly review rated the 2f text HIGH. Its point was the pairing, not the harness fact. This repo already publishes the Mac's permission mode, and the baseline accepts it. Next to that, an explanation of how a harness record interacts with permission rules reads as a description of one machine's current state. DOT-1 keeps assessments of that kind in the private repo, and `docs/decisions/DOT-4.md` already handles one the same way. The record type stays in the skill because an auditor has to know to look for it. The reasoning does not have to sit beside it.

**Why the entry is re-accepted, not withdrawn.** The review read the entry as resting on a control that no longer applies. Checked against the machine, the entry never rested on it. The allow-list's part in the acceptance is that it is empty: no rule pre-approves anything, for any tool. That holds however an agent is steered, because there is no rule to match or miss. Checked 2026-09-18, the user-level settings file has no `allow`, `ask` or `deny` rule and no hook. This repo tracks none and activation writes none. The PR gate and the pinned agent-instruction inputs are what bound an injection, and neither changed.

The review's reading was a fair one of the text. As accepted on 2026-09-07, the entry named three controls in one list, the empty allow-list among them, so this is a restatement of the acceptance and not only a clarification. The entry now names the gate and the pinned inputs as the two controls that carry it, and the empty list as a condition: what it does, and what it was never counted on to do. The first draft of this change added that paragraph below the old three-control sentence without editing it; the forge's review caught the contradiction, and both now say the same thing. It also gains a trip-wire the old one lacked: a permission rule for a single tool is not to be counted on as a control here without checking it against the private assessment first.

**Why this is the owner's call, and how it is put to them.** A baseline entry that is loosened is a decision about risk. This one is tightened in wording and unchanged in scope, but it is still an acceptance being restated by an agent. It ships as a pull request that CODEOWNERS routes to the owner. The alternative the review offered, recording the entry as no longer accepted, stays open to them: it would mean taking the mode line out of activation, or carrying an open finding in the private file.

**Not done here.** No history rewrite. The trimmed sentences stay in published history, for the reasons the baseline gives for its other history entries: a force-push does not remove objects the mirror already serves, and it would break every sha-pinned fleet checkout. No change to `nix-darwin/flake.nix`; the Mac's mode is as accepted.
